# CLAUDE.md Maintenance Skill — Design

## Problem

`makewhatis/rhapsody` has 25 nested `CLAUDE.md` files (root + 24 directories), generated by a
live-composed Claude Code `Workflow` run and merged via PR #35 (2026-08-27). Those files are
snapshots: as the repo's code changes, individual `CLAUDE.md` files can drift — a renamed
function, a changed placeholder name, a directory that no longer exists, a new crate that has no
file at all. Nothing currently detects this. This is sub-project #5 of the original nested-CLAUDE.md
initiative (sub-projects #1/#2/#4 — research, methodology spec, and the live generation run — are
done; #3, a separate `bo-mode` repo for reusable AI tooling, is out of scope here).

## Goal

A skill, checked into `makewhatis/rhapsody`, that detects and fixes `CLAUDE.md` drift with
*targeted* updates — not a full regeneration of the tree. It runs as a deliberately-dispatched
Rhapsody ticket (a "sweep"), not as a side effect of ordinary feature tickets.

## Non-goals

- Not a side effect of ordinary tickets. Only a dedicated sweep ticket opts into this.
- Not a CI gate. No `.github/workflows` change (also blocked today by the missing `workflow` OAuth
  scope — see root `README.md`'s Divergences / prior PR #34 notes).
- Not a full re-run of the original discovery methodology across the whole tree — that's
  regeneration, which this is explicitly trying to avoid.

## Architecture

Two pieces, split by what changes per-run vs. what's a standing trigger:

1. **`.claude/skills/claude-md-maintenance/SKILL.md`** (checked into `makewhatis/rhapsody`,
   alongside the existing project-adjacent skills `dogfooding-rhapsody` and
   `rhapsody-capabilities-sync` in `~/.claude/skills/` — this one lives in the *target* repo
   itself since its content is Rhapsody-tree-specific). Holds the full process below.
2. **A new entry in `~/.rhapsody/capabilities.yaml`**: `name: claude-md-maintenance`. Same shape as
   the existing 9 defaults (`code-review`, `deep-research`, etc. — see
   `crates/config/src/capabilities.rs::default_capabilities`). Its `instruction` field is a short
   pointer telling the dispatched agent to read and follow the repo-checked-in SKILL.md verbatim.
   You opt a ticket into it via a `rhapsody:claude-md-maintenance` Linear label (per the
   `rhapsody-create` skill's convention), and only ever on a dedicated sweep ticket.

**Why split this way:** `capabilities.yaml` entries are short, generic, machine-local trigger text
(per `rhapsody-capabilities-sync`'s existing convention) — not a place for a multi-step process.
The actual methodology belongs in the repo it operates on, versioned with the code it describes.

**Tool availability caveat:** the dispatched `claude` subprocess (`crates/agent/src/claude/args.rs`
`build_args`) sets no `allowedTools`/`disallowedTools` by default, so `Workflow` is available
unless the target project's config explicitly disallows it. `Workflow`'s own opt-in policy is
satisfied because a skill's instructions are telling the agent to call it — this doesn't depend on
the project having `ultracode: true` set, though that remains available as a belt-and-suspenders
option if a project wants to standardize on it.

## Process (what the SKILL.md documents)

Runs inside one unattended `claude -p` turn, dispatched by Rhapsody against a real Linear ticket in
`makewhatis/rhapsody`, inside that ticket's own forked git worktree.

**1. Scoped structural discovery** ("deep research," bounded to the delta since the last sweep, not
a from-scratch Phase A re-run). Find the newest last-touched commit among the 25 existing
`CLAUDE.md` files; `git diff` the whole tree since that commit, looking specifically for:
   - New directories that plausibly warrant a `CLAUDE.md` (a new crate under `crates/`, a new
     top-level subsystem) — apply the same depth/rationale judgment as the original methodology's
     Phase A structure step, just scoped to what's new rather than the whole tree.
   - Existing covered directories that were deleted or gutted to the point their `CLAUDE.md` is now
     pointing at nothing.

**2. Per-file drift check.** For each of the 25 existing files: `git log -1 --format=%H -- <file>`
for its own last-touched commit, then `git diff <that-commit>..HEAD -- <directory>` to see what
changed underneath it since. A file with an empty diff is skipped entirely — this is what keeps the
sweep "targeted updates," not regeneration. This mirrors the original methodology's Phase D
verification checks (no ancestor repetition, <200 lines, concrete claims, exact
`# CLAUDE.md — <path>` header) but only re-runs them where something actually moved.

**3. Fix drift via `Workflow`.** For files flagged by steps 1–2 (new files to draft, retired files to
flag for removal, existing files with confirmed drift): author and run a `Workflow` **inline**
(via the `script` parameter — never write a persisted `.claude/workflows/*.js` file, the same hard
constraint the original generation methodology used) that:
   - Drafts targeted edits depth-first — parents before children, so a child's non-repetition check
     sees the parent's *already-fixed* content, not its stale version.
   - Independently verifies each edit with a separate agent from the drafter, checking the same bar
     as the original Phase D: no repeated ancestor content, under 200 lines, concrete and
     non-derivable from reading the code directly, correct header.
   - One bounded redraft attempt on a failed verification; otherwise flag that file in the turn's
     final summary for human review rather than merging a low-confidence edit.

**4. Normal Rhapsody ticket flow.** Commit the changes, open a PR against `makewhatis/rhapsody` the
way any dispatched ticket does (this is a real GitHub-backed project, not the local-clone self-build
scenario `dogfooding-rhapsody` describes) and end with `HANDOFF: in-review`. No special-cased output
handling — this reuses the daemon's existing commit/PR/handoff mechanics.

## Testing

Dogfood it for real: deliberately edit something under one of the 25 currently-covered directories
in a way that makes its `CLAUDE.md` wrong (e.g. rename a function the file names by name), create a
real Linear sweep ticket with the `rhapsody:claude-md-maintenance` label, move it to `Todo`, and
confirm the resulting PR touches only the drifted file(s) with an accurate, targeted fix — not a
full-tree regeneration, and not silence.

## Open risk

This is the first capability whose instruction tells the dispatched agent to use the `Workflow` tool
itself — every existing default capability is a self-review/methodology nudge, not an orchestration
directive. If a target project's config disallows `Workflow` via `disallowedTools`, or the CLI
build in use doesn't expose it, the capability instruction becomes a no-op. Worth a real end-to-end
dogfood run (see Testing) before trusting this pattern for future capabilities.
